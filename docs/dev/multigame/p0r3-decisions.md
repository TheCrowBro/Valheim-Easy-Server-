# Phase 0': the choices made in the R3 contracts

Phase 0' (branch `mg/p0r3`, on multigame at 2d0f1a6) froze the contracts R3's streams build against: the observer list, the Status types, the R3 manager files with their signatures, the public methods the API calls, `routerports`, `discord.Webhook`, `waker.GameCommand` and the panel's game-module contract. This file lists every choice it made where the spec was silent or inconsistent, and settles each contract gap of [stream-notes.md](stream-notes.md), so the lead can accept or change them. Nothing here changes what Valheim or the old panel do: every existing test and R1's goldens pass unchanged, the only new calls on existing paths go to observers that do nothing yet, and the only visible difference is that `/api/status` carries the R3 keys 4.9 adds (inside `games`, and the six new top-level keys `TestStatusTopLevelKeys` allows), which the old panel ignores.

The signatures are pinned in `internal/manager/signatures_test.go` (the cross-stream functions and the public methods) and `internal/routerports/signatures_test.go`. A stream may fill in any body and add private helpers in its own files; changing a pinned signature goes through the lead and changes that file too.

## 1. The game contract (`internal/game/additions.go`)

Each gap the game streams found is settled with an optional interface, a shared type or a named value, so no adapter has to change.

1. **Monitor replay (VM 1).** `game.Replayer` (`Replaying(on bool)`) and `game.LogReader` (`FromLog()`) are optional Monitor interfaces now. The manager's local `replayer` and `fromLogReader` are aliases of them, so Valheim's Monitor keeps working with no change.
2. **Errors with a next step (VM 2).** `game.ActionError{Msg, Action, Data}`. `manager.ActionError` is now an alias of it (spec 4.3's `ActionError.Data`), so an adapter's error and the manager's own reach `web.fail` as the same type, and every existing `&ActionError{Msg, Action}` compiles. Valheim's own `ActionError` with `SuggestedAction()` is still converted by `actionOf`; moving Valheim to `game.ActionError` is VM/M3's choice (no visible change). Writing `"data"` in `web.fail` is stream API's (web is API's).
3. **Activity notes from Plan (VM 3, Terraria 4, Vintage Story 7).** `Env.Note func(kind, text string)` and the nil-safe `Env.AddNote`. One per instance rather than a `PlanRequest` field, because the Installer, `After` and stop steps need it too, and the manager can stamp the instance on each entry. It never takes the manager's lock; Monitors keep reporting through `Event.Text`. The legacy instance's `Env.Note` is wired to `addGameActivity`; Valheim still uses `LegacyStore.Note` (unchanged).
4. **A Candidate adapters may import (Minecraft 1, Necesse 2).** `game.Candidate` is a type alias of `worlds.Candidate`, so an adapter writes `worldstore.Format`'s `Detect` and `Place` with it without importing `internal/worlds` (still Valheim-only by `TestImportRules`). worldstore is unchanged: it is the same type.
5. **"Needs Windows" decided at run time (Minecraft 2, spec 10.2 Q6).** `game.Supporter` (`Support() (Level, string)`) on a Server, asked only when `Info.OS` says it runs, never in fake mode, with the manager's lock held (so it answers from memory or `Store().Get()`). `Info.LevelOn(goos, goarch)` reads `Info.OS`/`NeedsText` with the spec's "exact key wins, missing = can't run" rule. Add a game can't know a Java problem before the install, so the catalog uses `Info.OS` alone; once installed, the game's page shows the reason instead of Start. The OS refusal must never apply to the legacy instance, which has always run wherever the app runs (M3's start path; Valheim's `Info.OS` also lists `linux`, where the tests run).
6. **A licence to accept (spec 5.2, 6.2's catalog `eula?`).** `game.Licensed` (`EULA() string`, the link) on the Game, because Add a game shows the box before there is an instance. The manager writes the time into `Saved.State[game.StateEULA]`.
7. **State keys other code writes (Minecraft 3).** `game.StateEULA = "eula"` (written by A's `AddGame`, and by a new `eula` field of the settings change for an instance that lost it, such as one rebuilt from its folders, 3.4) and `game.StateCGNAT = "cgnat"` (`"true"` while the router check finds carrier-grade NAT, absent otherwise; written by N's `noteNAT` into every non-legacy instance's State, never the legacy one, whose State would mean settings.json). State rather than a new `PlanRequest` field because Minecraft already reads it, and the last answer survives an app restart, so a start before this run's check still has one; absent means the allow list goes on, the safe side. `allowListOn` and Zomboid's `adminPassword` stay the adapters' own keys.
8. **New event kinds (Minecraft 4, Terraria 3, Zomboid 4, Vintage Story 4, Enshrouded 3).** The kinds stay open strings. `game.Kind…` names the shared ones the manager reacts to (`online join leave death saved stopping count code turned_away`). Any other kind is the game's own: the manager shows an event with `Text` in the feed under its kind and does nothing else; the game's panel module gives it an icon, and a kind without one shows as a warning. The kinds used so far are listed in `internal/web/ui/assets/games/README.md`.
9. **World "" means the selected world (Enshrouded, after review 2).** Said now in the comments of `Validate` and `Fingerprint` in `contract.go`. Adding that check to `gametest.Conformance`, and fixing the same bug in `gametest/demo`, are stream F's files (below).
10. **The RCON stop step (F 2).** `StopStep`'s comment now says what gametest already does: connect to 127.0.0.1 on `Record.Ports["rcon"]` with `Record.Secrets["rcon"]`; a refused connection moves on at once, a hang-up after the command gets the step's Wait (RC 2).

Not settled here, and why:
- **Adapters importing `internal/discord` (VM 5):** left as it is. Valheim's copy of `Escape` has a test that keeps it equal, and keeping `discord` out of adapters keeps every post in the manager's queues.

## 2. The manager

### The observer list (`hooks.go`, spec 4.1)

- Four observers, one per stream, in this order: `lifecycleObserver` (autostop.go, A), `askObserver` (ask.go, D), `wakerObserver` (waker.go, WK), `routerObserver` (router.go, N). A comes first, so auto-stop is decided before the others in a tick. Each is written out with all seven methods, empty, so each stream sees every hook. The list is built in `New`; a test can append its own (`hooks_test.go`'s recorder).
- The fixed points, all with `m.mu` held:
  - `onJob`: in `launchJobAs` when a job starts and when it finishes (`inst` nil for the app slot).
  - `onReady`: in `handleEvents` when a run becomes ready while the app follows it live. A taken-over run gets `onTakeover` instead; if it only becomes ready after the catch-up, `onReady` follows. So each run gets exactly one of the two at the moment it is known to be ready.
  - `onEvent`: in `handleEvents`, for each event of a live line or tick, after the manager has noted it. Not for events read back after a takeover, nor for the leaves at the end of a run.
  - `onTakeover`: in `caughtUp`, once the app has caught up with a taken-over server's log.
  - `onExit`: in `onExit`, after `inst.run` is cleared and the stopped post is queued. **A change from 4.1's signature:** it is `onExit(inst, run *serverRun, exit)`, not `onExit(inst, exit, auto bool)`. The observer is given the run that ended, because `inst.run` is already nil by then and the run holds what N and A need: `run.mappings` and `run.rec.Ports` (N unmaps them), and `run.autoStopped` and `run.autoReason` (A can tell an auto-stop from the ask rule's stop). So `auto` is `run.autoStopped`, and the spec's `serverRun.mappings` is where N keeps a run's mappings.
  - `onTick`: in power.go's `sampleLoop`, after the usage sample and before `checkIdle`; not on the tick that notices a wake-up.
  - `onWake`: `wakePurpose` in `wokenOnPurpose` (power.go); `wakeTagged`/`wakeUntagged` in `wakeSignal` (wakesignal.go) for every packet heard, repeats included. In this build a packet for another game is dropped before `wakeSignal`; WK changes that.
- A panic in an observer is logged and contained; the lock stays with the caller. Observers act by starting work with `m.go_`.
- **Quiet jobs and auto-stopped exits** (spec 4.5), placed in M3's files so A and D needn't edit them: `runQuietJob` (via `launchJobAs`) doesn't reset `machineIdleSince`; `onExit` doesn't reset it when `run.autoStopped`, picks the stopped post's reason from `run.autoReason`, and writes A's `autoStopActivityLocked(run)` as the activity entry in place of "The server stopped." ("Minecraft stopped: nobody played for an hour.", from `run.autoMinutes`; for the ask rule, where the spec gives no activity text, "Windrose stopped: nobody answered for 2 hours.", the same reason as its Discord line). New stop reasons `stopIdle` and `stopAsked` are appended to the list (so the old values are unchanged); `stoppedText` falls to its default for them until D writes their texts.

### Fields and state

- The R3 fields of spec 4.1 are on `instance` (`foreign`, `history`, `byPlayers`, `emptySince`, `ask`, `cache`) and `serverRun` (`stdin`, `autoStopped`, `memNow`, `probeFails`, `mappings`), each commented with the stream that fills it. Additions: `serverRun.autoReason` (idle or asked, for the stopped post), `serverRun.autoMinutes` (the auto-stop minutes the stop was decided with, so the texts stay right if the owner changes the setting while the game stops) and `serverRun.cpuNow` (the Status `cpu`).
- The Manager's R3 fields of 4.1 (`servers`, `safeMode`, `lan`, `resumeSet`, `wakeAsked`, `wakeTags`) are there. **Each stream also gets one state struct of its own type, in its own file**, so it never edits manager.go: `lifeState` (power.go, A), `discordState` (discord.go, D), `askState` (ask.go, D, per instance), `routerState` (router.go, N); WK keeps `wakerState`. `instCache` (instance.go) is M3's.
- `Activity.Game` (`game`, omitempty, spec 1.3) and `addGameActivity` are added; nothing sets it yet, so activity.json is unchanged.
- `m.instances` and `m.order` are still read without the lock; M3 must guard them before Add a game changes them (`addInstanceLocked`, `removeInstanceLocked`).

### Files and who calls whom

- Every R3 file of 9.3 exists with signatures and empty bodies: A's addgame.go, remove.go, memory.go, autostop.go, ports.go, firewall.go, resume.go (and R3 additions at the end of power.go); D's ask.go (and additions to discord.go and records.go); WK's additions to waker.go; N's router.go. Bodies answer "nothing" (nil, 0, an empty list) or `errNotYet` ("This part of the app isn't finished yet."), so no stub changes what R2 does.
- **`FixFirewall` moved unchanged from status.go to firewall.go**, so stream A owns the all-games firewall fix without editing M3's file.
- M3's shared helpers are in the new games.go: `instanceByID`, `newGameInstance`, `addInstanceLocked`, `removeInstanceLocked`, `updateServers`, `starsLocked`, `isStarredLocked`, `isDisabledLocked`, `isHiddenLocked`, `canRunLocked`, `presenceProvenLocked` (the legacy instance only, until M3 adds the probe and `presenceSeen`), `portChosenLocked` (the legacy game's ports count as chosen: they come from its own settings, and the app never picks them), and `startGameWith`, the one start path. 4.3's steps are wired now, so stream A only fills in bodies in its own files: `startGameWith` runs the legacy start's checks (`startChecks`, split out of `startGame` in server.go, unchanged), then A's `memoryForStartLocked(inst, o)` (memory.go: `memoryCheckLocked` unless `o.Memory` is "anyway" or `o.Source` is `SourceRestart`; a "stop:<id>" skips the check, and answers `errNotYet` until A builds it, rather than starting without stopping anything), then the start job (`runStartJob`), whose first step is A's `memoryInStartJob(ctx, j, inst, o)` (memory.go, empty: where "stop:<id>" stops that game inside the start job). `doStart` calls A's `checkPorts` after `Plan` and before the launch for every instance but the legacy one, which keeps its check inside its Plan. M3 adds the rest of step 1 (foreign, hidden, disabled, can't run here) to the checks and moves start-with-app, crash restarts and the resume onto this path. `StartServer` (the old routes, the tray) still calls `startGame` directly, which never checks memory, so Valheim starts exactly as before.
- Cross-stream calls given a signature now: A's `autoStopGame` (used by D's ask rule with `stopAsked`), `autoStopText` (used by D's stopped post; implemented, as the spec gives its exact rule: "an hour" at 60, "2 hours" at 120, else "<n> minutes", so 180 is "180 minutes"; `TestAutoStopText`), `autoStopActivityLocked` (called by M3's `onExit`; implemented), `memoryCheckLocked`, `memoryForStartLocked` and `memoryInStartJob` (called by M3's `startGameWith`), `runningGamesLocked` (also WK's memory reply), `startFromWake` (called by WK), `scheduleResume`, `resumeNow` (called by WK), `cancelResumeLocked`, `networkBack`, `pickPortsLocked`, `reservedPortsLocked`, `checkPorts`, `checkChosenPortsLocked`, `gameRulesLocked`, `checkGameFirewalls` (called by M3's checks loop); D's `gameLinkLocked` (used by WK), `gameDiscordLocked`, `setGameDiscord` (used by M3's settings); WK's `wakerCommandsLocked`, `starsChanged` (called by M3's `SetStar`), `wakeReply`; N's `routerStatusLocked`, `routerSummaryLocked`, `unmapPorts` (called by A's remove), `routerPortsChanged` (called by M3's app settings), `noteNAT`.
- `restartGame`, `forceStopGame` and `installGame` were extracted from `RestartServer`, `ForceStop` and `InstallServer` (same code; the legacy methods call them), so the `…Game` forms work per instance.

### Public methods (spec 4.1, 6.2)

- Named with the spec's "`…Game`" rule where an old method exists (`StartGame`, `StopGame`, `RestartGame`, `ForceStopGame`, `InstallGame`, `CancelGameJob`, `WorldsGame`, `SelectWorldGame`, `CreateWorldGame`, `SetWorldValuesGame`, `DeleteWorldGame`, `BackupWorldGame`, `RestoreWorldGame`, `RenameWorldGame`, `PrepareDownloadGame`, `ExportBackupGame`, `NewUploadGame`, `UploadGame`, `FinishUploadGame`, `DiscardUploadGame`, `ImportUploadGame`, `LocalWorldsGame`, `ImportLocalGame`, `KnownPlayersGame`, `ListsGame`, `SetListGame`, `LogsGame`, `CurrentLogPathGame`, `HistoryGame`, `ByPlayersGame`, `ResetStatsGame`, `RecordsGame`), and plainly otherwise (`StopAll`, `SetStar`, `SetSidebar`, `GameSettings`, `UpdateGameSettings`, `UpdateAppSettings`, `AllowPlayer`, `Catalog`, `CatalogLocal`, `AddGame`, `RemoveGame`, `PickPorts`, `KeepOn`, `SetMainDiscord`, `TestGameDiscord`, `Router`, `CheckRouter`).
- For the legacy instance a `…Game` form calls the old method, so the API stream can serve Valheim through the new routes from day one; any other instance, and methods with no old form, answer `errNotYet` until their stream fills them in. `StartGame` is the exception: it takes `startGameWith` for every instance (above), so the legacy game started from the new panel gets the memory step as the spec says, while `StartServer` does not (`TestStartGameTakesTheR3Path`). `StopAll` already stops every running instance (each in its own job, so they stop at the same time); `ListsGame` reads the legacy game's lists through `game.Lister`; `TestGameDiscord(link, "")` is today's `TestDiscord`.
- Request and view types carry JSON tags so the API can decode and encode them directly: `StartOptions` (`memory`; `Source` is set by the caller, never read from JSON, with `Source…` constants), `GameSettingsView`/`GameValues`/`PortSetting`, `GameSettingsChange` and `AppSettingsChange` (pointer fields: only what is set changes), `GameDiscordSettings`/`GameDiscordChange` (D's file), `GameWorldsView`/`WorldSchemas` (with the legacy game's `options` and `mods` as well, omitted for others, so the Valheim module can keep its world-card controls), `GameList` (`{kind, ids}`), `CatalogGame`, `AddGameRequest`/`AddWorld` (`candidate` is a `CatalogLocal` candidate's ID)/`AddedGame`, `MemoryShort`/`RunningGame`, `RouterView`/`RouterMapping`/`SteamSeen`.
- Additions to 6.2's bodies: `eula` in the settings change (item 7 above), and `ResetStatsGame` (the legacy Stats page has a reset).

### Status (`status_games.go`, spec 4.9)

- `GameStatus` has every field of 4.9. `gameStatusLocked` asks one hook per stream: `autoStopStatusLocked` (A, `AutoStopStatus` in autostop.go), `askStatusLocked` (D, `AskStatus` in ask.go), `routerStatusLocked` (N: the router state by role, for each public port's `router` and for `JoinInput.Router`), `discordStatusLocked` (D, `GameDiscordStatus` in discord.go). Each part's type lives in its stream's file, so the stream owns its JSON; `RouterStatus` (the top-level `router`) is in status_games.go as the spec says, filled by N's `routerSummaryLocked`.
- The top-level R3 keys (`stars`, `sidebar`, `online`, `playing`, `router`, `safeMode`) are in Status now, as `TestStatusTopLevelKeys` allows. With no servers.json yet they read `[]`, `{activeOpen: true, inactiveOpen: false}`, the games online and the people playing, `null` and `""`, so Valheim shows unstarred until M3's first start writes `stars: [<legacy id>]` (3.4); the UI's fixtures should show it starred, as R3 will. The old panel ignores all of them.
- Status works out the legacy instance's adapter calls once (`gameView`) and shares them between its old top-level fields and the legacy `GameStatus`, so the adapter isn't asked twice. So the spec's `gameStatusLocked(inst)` is `gameStatusLocked(inst, view)`; `gameViewLocked(inst, lan)` makes the view of a non-legacy instance from the caches (M3 finishes it: today's `installedLocked` still looks at the disk for every instance). `jobs` needed no new type: Status's `jobs` (R2) lists `Job`s, which already carry `game`. A `GameStatus` keeps R2's `count` (0 when stopped) and has `reminder: []` and `warnings: []` rather than null.

## 3. Other packages

- **`internal/routerports`** (N's): the types and signatures of 6.5 with stub bodies (`errors.ErrUnsupported`; `NAT` answers ""). Added: `SteamServer`'s fields (from Steam's `GetServersAtAddress` answer: `addr`, `gameport`, `appid`, `gamedir`, `steamid`, `secure`, `lan`), and `ErrForwardedByHand` (the UPnP 718 conflict whose entry points at this computer: counts as open), `ErrConflict` and `ErrNoRouter`, so the manager can tell the cases apart.
- **`discord.Webhook`** (D's package): implemented, not stubbed, in a new file webhook.go: the same request as `Guild`, also reading `channel_id`; `Guild` is unchanged. Tested against a stand-in.
- **`waker.GameCommand`** (WK's package) in games.go, and `Config.Games *[]GameCommand` with the tag `json:"games,omitempty"`. On a pointer, omitempty drops only nil, so an empty list is still written as `[]`, which is what 6.4 asks for ("no omitempty" was written with a plain slice in mind). Every config this build writes stays byte-identical until WK sets `Games`. `TestConfigGames` pins the three meanings (absent, `[]`, a list).
- **wol:** nothing new was needed: `wol.PacketFor` and `wol.GameOf` are there (SV); sending a game's packet is inside WK's own wol.go.
- **The panel's module contract** (`internal/web/ui/assets/games/README.md`): 6.1's object, with these choices: a module whose file is missing or fails to load leaves the defaults; `id` must equal the file name; `feedIcons` values may also be `[icon, tone]` like the shell's own; tab modules have the shape of today's page modules (`render(app, game)`, optional `mount`, `unmount`, `afterRender`, `title`) and may live under `games/<id>/`; modules may import `../dom.js` (UI keeps its exports) but never another game's module; all state is keyed by `game.id`; the draw hooks are called every refresh and must not call the API. One hook was added: **`checklist(game, h)`**, for setup-checklist rows only one game needs (Minecraft's RCON note on a Mac, which G-minecraft said belongs to its module; 6.1's Home mentions game-specific checklist notes). The README is embedded with the rest of `ui/` and served as a plain file like any asset; renaming it `_README.md` would leave it out of the program if the lead prefers.
